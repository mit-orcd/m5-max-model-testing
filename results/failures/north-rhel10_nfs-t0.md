- **NFS over TLS support (new feature)** – RHEL 10 now provides full TLS encryption for NFS RPC traffic, relying on kernel TLS (kTLS) (Technology Preview). This change enhances security by encrypting client‑server communication, but it may add encryption overhead that can affect performance; administrators can weigh the security benefit against any latency impact.

- **IPv6 address handling in nfs:// URLs (bug fix)** – The parsing of IPv6 addresses enclosed in square brackets (e.g., `nfs://[2001:db8::1]/`) was broken, causing ReaR to abort with “Invalid scheme”. The fix correctly interprets the brackets, allowing IPv6 addresses in BACKUP_URL/OUTPUT_URL without requiring backslashes. This restores usability and prevents premature failures when using IPv6‑addressed NFS servers.

- **Client‑side NFS caching via FS‑Cache (new performance feature)** – A new mount option enables NFS shares to be cached locally using the FS‑Cache framework (backed by `cachefilesd`). Cached reads are served from the client’s local storage, dramatically reducing network traffic and server load. The feature can improve overall NFS client performance for frequently accessed data, though it may add CPU/memory overhead for cache management.

- **`vers` mount option clarified (compatibility fix)** – The `vers` option is now documented as identical to `nfsvers`, ensuring consistent behavior across tools and reducing configuration errors. While it does not change performance, it simplifies correct version selection, helping administrators avoid mis‑configured mounts that could lead to suboptimal performance.

- **cachefilesd service prerequisites updated (performance enablement)** – Documentation now specifies that the cache back‑end must be an `ext3`, `ext4`, or `xfs` file system mounted at `/var/cache/fscache/` with extended attributes (default on RHEL 8+). This ensures the caching infrastructure works correctly, allowing the new FS‑Cache NFS feature to deliver its performance benefits.
